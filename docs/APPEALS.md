# Апелляции и пересмотр

Любая оценка в Revengers CQA — аргумент, который можно проверить, оспорить и исправить. Этот документ описывает процесс апелляции, статусы, четыре исхода решения, независимость проверяющего, цикл обучения и метрики споров.

## 1. Предпосылка: прослеживаемость

Апелляция возможна только потому, что каждый балл **прослеживается до реплик**: у любого ответа есть доказательства (номер строки, цитата), проверенный участок для «Нет», условие для N/A, применённое правило и уверенность. Проверяющий спорит не с «мнением модели», а с конкретными строками транскрипта.

## 2. Процесс

```
Оператор                         Система                              Проверяющий
───────────────────────────────  ───────────────────────────────────  ─────────────────────────────────
открывает карточку
выбирает критерий → «Оспорить»
пишет комментарий ─────────────▶ Appeal{status:'open'}
                                 Evaluation.status → 'under_appeal'
                                 исходная оценка остаётся видимой
                                 оценка исключена из рейтингов  ────▶ очередь: open первыми, затем по
                                                                      возрастанию уверенности
                                                                      видит спорную оценку, комментарий,
                                                                      доказательства, фрагмент ±3 реплики
                                 (опц.) «Второе мнение» — нейтральный
                                 черновик от модели, не решение
                                                                      Подтвердить / Изменить + исход + причина
                                 пересчёт итога общим движком
                                 history += decision
                                 Evaluation.status → 'reviewed'
карточка: исходная → решение → финал
```

Роли «Оператор» / «Проверяющий» — переключатель в шапке интерфейса (без входа в систему, как разрешено условиями задания). Подача апелляции и решение по ней — **отдельные действия** в интерфейсе.

## 3. Статусы

| Объект | Статус | Значение |
|---|---|---|
| Appeal | `open` | подана, решение не принято |
| Appeal | `confirmed` | проверяющий подтвердил оценку |
| Appeal | `changed` | проверяющий изменил оценку |
| Evaluation | `final` | оценка модели, споров нет |
| Evaluation | `under_appeal` | есть открытая апелляция; метка «под апелляцией» везде, где показан балл |
| Evaluation | `reviewed` | по всем апелляциям есть решения |

## 4. Четыре исхода решения

| Исход | Код | Что происходит |
|---|---|---|
| Балл изменён | `score_changed` | проверяющий задаёт новое значение; итог пересчитывается тем же движком (`packages/scoring`); исходный балл сохраняется как `ai_original` |
| Критерий нужно менять | `criterion_change` | балл меняется или остаётся, но спор указывает на дефект формулировки; сигнал для редактора чек-листа |
| Оценка верна — пробел в объяснении | `stands_explanation` | балл остаётся; проверяющий дописывает объяснение, понятное оператору |
| Оценка верна — коучинг | `stands_coaching` | балл остаётся; случай становится материалом для обучения оператора |

Каждое решение требует **причину** (`reviewer_note`). Решение необратимо для данной апелляции; новая апелляция по тому же критерию допускается и ссылается на предыдущую историю.

## 5. Независимость

- Проверяющий — **никогда не тот, кто выставил оценку**: оценку ставит модель, решение принимает человек.
- «Второе мнение» модели — опциональный нейтральный черновик (предложение + обоснование на русском). Оно помечено как черновик, не меняет статусов и не считается решением.
- Исходная оценка остаётся видимой во время спора и после решения.

## 6. Пересчёт и история

Решение «Изменить» заменяет ответ одного критерия и прогоняет **весь** расчёт заново через общий движок: эффективные веса, итог, секции. В карточке показаны `original_total → total` и журнал `history`: `evaluated` (ai) → `appeal_opened` (operator) → `decision` (reviewer) с `from`, `to`, `total_before`, `total_after`, `note`.

Пример из демонстрации: `p1-ru-007`, критерий 04, «10 из 20» → «15 из 20», исход `score_changed`, итог 70.00 → 77.69.

## 7. Цикл обучения (без дообучения модели)

Подтверждённые решения проверяющего становятся **ограниченными примерами** для модели-судьи: по каждому критерию в промпт добавляется до 5 последних решений (`Example{criterion_id, excerpt, final, reviewer_note, outcome}`). Модель не дообучается; меняется только контекст. Эффект измеряется на отложенной выборке и показывается на странице «Калибровка» («учтено решений проверяющего: N», согласие до/после). Честная формулировка: «система учится на решениях ваших проверяющих», не «становится умнее сама».

После исхода `score_changed` система предлагает «проверить похожие»: оценки того же критерия с той же меткой и низкой уверенностью.

## 8. Метрики споров

На странице «Апелляции» и в `/api/stats.disputes`:

- объём споров (всего / открытых);
- доля подтверждённых (`upheld_share`) — высокая доля подтверждений при большом объёме = оператору не хватает объяснений, низкая = модель ошибается;
- кластеризация по критерию — несколько изменённых оценок по одному критерию = **дефект формулировки критерия**, повод для редактора чек-листа;
- распределение по исходам.

Оценки с открытой апелляцией **исключаются из рейтингов операторов** до решения (`operators[].excluded_open_appeals`).

## 9. Ограничения использования

- Решение по апелляции принимает человек; система предлагает, но не решает.
- Результаты и решения поддерживают коучинг и контроль качества. Автоматических кадровых решений система не принимает и не рекомендует.
- Апелляция рассматривается по тексту транскрипта; эмоции и интонации не выводятся.
- Срок рассмотрения (SLA) — организационная настройка команды качества; в прототипе отображается только возраст апелляции.
