# Стоимость и время оценки (COST)

Политика проекта — **нулевые затраты команды на вызовы моделей**. Каждая цифра ниже взята из файла в репозитории; имя файла указано рядом. Ничего не оценивается «на глаз». Там, где цифра — расчёт по прайс-листу, а не понесённый расход, это написано словом **ОЦЕНКА**.

## 1. Что измерено

Основной провайдер — **Alem Plus** (llm.alem.ai, OpenAI-совместимый API). **0 ₸ для команды — API Alem Plus (llm.alem.ai) по ключам, предоставленным организаторами хакатона; публичные тарифы платформы не опубликованы, стоимость в продакшене требует уточнения.** Роли: судья `qwen3-8` (режим «thinking» выключен через `chat_template_kwargs.enable_thinking=false`, см. `services/evaluator/providers/alem.js`), проверяющая модель `gpt-oss`, казахское второе мнение `kazllm`, резерв `alemllm`. Для команды каждый вызов — **0 ₸** (`cost_usd: 0` в трассе); токены и задержка записываются в трассу (`trace.calls[]`), поэтому объём для будущего расчёта цены известен.

### 1.4 Цена изменения одного критерия — `reports/runs/alem_qwen3-8_v3_c06.json` и `_v5_solo06.json`

- **v3** (история): после уточнения подсказки к ступеням 06 в `config/checklist.v1.json` ключ кэша изменился только для 06 — **67 вызовов** = 65 судья (только 06) + 2 repair; kz пропущено; `cache_hits: 455`. Токены 212 092 + 8 702 вход / 20 479 + 869 выход. Время 152,7 с (6,9 с на диалог среднее).
- **v5** (история): тот же масштаб — 65 вызовов судьи только по 06 + 15 kz, `cache_hits: 455`, 114,4 с.

Это измеренная цена изменения одного критерия: один вызов на диалог, а не восемь. Изменение **только веса** стоит **ноль вызовов**: вес не входит ни в ключ кэша, ни в промпт, поэтому это чистый пересчёт движком. Изменение общей политики (как в v4 и v6) меняет ключ кэша всех критериев и стоит полного прогона.

**Книга вызовов Alem Plus** (все файлы в `reports/runs/`): v1 138 + дооценка ≈ 3 + v2 82 + v3 67 + test–retest и инъекция 21 + v4 86 + v5 80 + v6 143 + проверка `gpt-oss` судьёй на holdout 47 = **≈ 667 живых вызовов** за всю разработку; все калибровки, экспорт результатов и демо-пути — из кэша.

## 2. Квота и как продукт её бережёт

Заголовки ответа Alem Plus показывали лимит **200 запросов** (читаются `readQuota()` в `services/evaluator/providers/alem.js`: `x-ratelimit-*-remaining/limit`); окно сброса **неизвестно** (за разработку сделано ≈ 667 вызовов, то есть лимит восстанавливается, но когда — не измерено). Полная оценка 65 диалогов текущим продуктом стоит 143 запроса (v6) — большая часть лимита. Поэтому:

1. **Кэш по критерию** (`data/cache/eval/`, ключ = sha256(строки диалога, определение критерия **без веса**, политика, версия промпта (для отдельно оцениваемых критериев — своя), модель)). Повторная оценка, пересчёт отчёта, новая версия чек-листа с неизменными критериями, изменение весов — 0 вызовов. Все 65 DEV-диалогов закэшированы и закоммичены.
2. **Мало вызовов судьи на диалог**: один по всем критериям + один по каждому критерию из `CQA_JUDGE_SOLO` (по умолчанию только 06); батчирование по 3 критерия — только для локальных моделей ≤ 8B (`CQA_JUDGE_BATCH`).
3. **Валидатор и автоисправление без модели**; повторный запрос — максимум один, только по нарушенным критериям (в v6 — 0 диалогов, в v4 — 9 %); дальше — консервативный ответ по правилам, а не третий вызов.
4. **Проверяющая модель только для неуверенных результатов**: для alem по умолчанию `CQA_VERIFY=low` — проверяются результаты с уверенностью < 0,75 (`CQA_VERIFY_THRESHOLD`).
5. **Резерв**: при остатке ≤ 20 % лимита (или `CQA_ALEM_RESERVE` запросов) судья автоматически переключается на резервную модель `fallback`; при 429 — пауза `retry-after` и переключение; при отказе провайдера — деградация к правилам с пометкой в `review_reasons` и честной подписью происхождения (`heuristic-fallback`, «модель недоступна»).
6. **Офлайн-режим** (`CQA_PROVIDER=offline`; он же выбирается по умолчанию, если не настроен ни Alem Plus, ни локальная модель): воспроизведение из кэша; промах — явная ошибка, а не тихий вызов. Калибровка имеет флаг `--cache-only`, который отказывается стартовать, если потребовался бы хотя бы один живой вызов (проверку инъекции он пропускает и переносит последнее живое измерение).
7. **Правила вместо модели там, где они точнее** (`config/routing.json`: 03, 07) — модель всё равно вызывается, её ответ по этим критериям используется как второе мнение; правка правила не требует вызова.

## 3. Каскад (одна оценка = диалог × версия чек-листа)

1. **Факты** (0 вызовов): первая/последняя реплика оператора, событие подтверждения личности и устная идентификация в звонках, сигналы раскрытия/оскорбления/обхода, ожидания (от последнего сообщения клиента), обрыв.
2. **Кэш** по критерию.
3. **Судья** — 1 вызов на диалог по всем критериям, кроме 06, + 1 вызов по 06.
4. **Валидатор** (0 вызовов) → автоисправление (в т.ч. защита 02: нет вопроса оператора → N/A) → при оставшихся нарушениях один `repair` → консервативный ответ по фактам с уверенностью ≤ 0,5.
5. **Проверяющая модель** — только для неуверенных результатов; расхождение понижает уверенность и попадает в `review_reasons`.
6. **KZ-диалоги** — второе мнение `kazllm`, 1 вызов на диалог по всем критериям, оценённым моделью при этой оценке; расхождение понижает уверенность и попадает в `review_reasons`.
7. **Маршрутизация** (0 вызовов): 03 и 07 решают правила, модель — второе мнение; остальные шесть решает модель.

Измерено: **2,2 вызова на диалог** (143 / 65, один проход v6) при выключенной проверяющей модели: 2 вызова судьи на диалог (129 на 65) + 1 `kazllm` на KZ-диалог (14) + 0 повторов.

## 5. ОЦЕНКА (не понесённые расходы): тот же объём токенов на платной модели

Формула — измеренные токены из `reports/runs/alem_qwen3-8_v6_rules.json` × цены за 1M токенов из `services/evaluator/pricing.js` (цены записаны разработчиками; перед цитированием жюри сверить с действующим прайс-листом поставщика — дата сверки в репозитории не зафиксирована):

```
cost_run      = (T_in × P_in + T_out × P_out) / 1e6
cost_dialog   = cost_run / 65
cost_month(N) = cost_dialog × N
T_in = 673 628, T_out = 136 580  (судья по всем критериям, кроме 06, + судья по 06 + kz, один проход v6,
                                    повторов 0, проверяющая модель выключена)
```

| Модель (прайс-лист `pricing.js`, $/1M вход / выход) | cost_run | cost_dialog | N = 50 000/мес | N = 100 000/мес |
|---|---|---|---|---|
| `claude-haiku-5-5` ($0,10 / $0,50) | $0,136 | $0,0021 | ≈ $104 | ≈ $209 |
| `claude-sonnet-5-5` ($2 / $10) | $2,71 | $0,042 | ≈ $2 087 | ≈ $4 174 |
| `claude-opus-5-5` ($4 / $20) | $5,43 | $0,083 | ≈ $4 174 | ≈ $8 348 |
| Alem Plus `qwen3-8` (измерено) | **$0 для команды** | **$0** | публичные тарифы не опубликованы — цена в продакшене требует уточнения | |

Для сравнения (история): по токенам прогонов v4 + v5 (два шага, лишние вызовы `kazllm`, 6 повторов) та же оценка давала $0,0025 / $0,050 / $0,101 на диалог, по токенам прогона v2 (один вызов судьи, прежняя политика) — $0,0017 / $0,034 / $0,068. Не учтено: проверяющая модель (выключена; при `CQA_VERIFY=low` < 1 вызова на диалог ≈ 4k/0,5k токенов) и кэширование промпта у облачных провайдеров (системный промпт ≈ 3–4k токенов повторяется в каждом вызове — реальная цифра была бы **ниже**).

Пропускная способность на Alem Plus: 1 094,5 с на 65 диалогов (v6, оба вызова судьи и казахское мнение) → ≈ 5 100 диалогов/сутки с одного процесса, если квота позволяет; реальный предел задаёт квота, а не время.

## Summary (EN)

Zero-spend policy for the team. Cost wording: **0 ₸ for the team — the Alem Plus API (llm.alem.ai) with keys provided by the hackathon organizers; the platform's public prices are not published, so production cost still has to be confirmed.** Current product cost, measured with judge `qwen3-8` (thinking off) on 65 DEV dialogs in one cold-cache pass — run `reports/runs/alem_qwen3-8_v6_rules.json` (night of 8 November): **143 calls** (129 judge — one call for all criteria except 06 plus one for 06 — 14 Kazakh second opinions, 0 repairs, 0 verifier) = 2.2 per dialog, **673 628 input / 136 580 output tokens** (≈ 10.4k / 2.1k per dialog), **1094.5 s wall ≈ 16.8 s/dialog throughput**, mean per-dialog latency 33.5 s (median not persisted), 0 USD for the team. History: the two-step v4 + v5 measurement on the previous policy took 166 calls and 535.8 s; the validator fix (model N/A read correctly) cut calls 138 → 82 (−41 %) and repairs 92 % → 3 % (`alem_qwen3-8.json` vs `_v2.json`). Changing one criterion re-judges only that criterion (v3 and v5: 65 judge calls, 455 cache hits); changing only a weight costs zero calls because the weight is in neither the prompt nor the cache key; a change to the shared policy text (v4, v6) re-judges everything. Checking `gpt-oss` as judge on the 20-dialog holdout took 47 calls and was clearly worse (MAE 15.73 vs 6.37). Total live calls over the whole project ≈ 667. Quota header: 200 requests, unknown reset window — protected by the per-criterion cache (all 65 dialogs cached; every later calibration and the organizers' `results/dev/results.json` export ran with 0 calls), few judge calls per dialog, at most one repair, verifier only for low-confidence results, 20 % reserve with automatic fallback, honest provenance when rules stand in for the model, strict offline mode (also the default when nothing is configured). §5 is a list-price **ESTIMATE, not incurred**: the v6 token volume would cost about $0.0021 (Haiku) / $0.042 (Sonnet) / $0.083 (Opus) per dialog using prices recorded in `services/evaluator/pricing.js` (re-verify against the vendor price page before quoting).
