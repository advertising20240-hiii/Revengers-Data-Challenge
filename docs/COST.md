# Стоимость и время оценки (COST)

Политика проекта — **нулевые затраты на вызовы моделей**. Каждая цифра ниже взята из файла в репозитории; имя файла указано рядом. Ничего не оценивается «на глаз». Там, где цифра — расчёт по прайс-листу, а не понесённый расход, это написано словом **ОЦЕНКА**.

## 1. Что измерено

Основной провайдер — **alem.plus** (Казахстан, OpenAI-совместимый API, бесплатный доступ). Роли: судья `qwen3-8` (режим «thinking» выключен через `chat_template_kwargs.enable_thinking=false`, см. `services/evaluator/providers/alem.js`), проверяющая модель `gpt-oss`, казахское второе мнение `kazllm`, резерв `alemllm`. Стоимость каждого вызова — **0 ₸**; токены и задержка записываются в трассу (`trace.calls[]`).

## 2. Квота и как продукт её бережёт

Заголовки ответа alem.plus показывали общий лимит **200 запросов** (читаются `readQuota()` в `services/evaluator/providers/alem.js`: `x-ratelimit-*-remaining/limit`); окно сброса **неизвестно**. Один полный прогон 65 диалогов стоил 138 запросов — то есть **почти всю квоту**. Поэтому:

1. **Кэш по критерию** (`data/cache/eval/`, ключ = sha256(строки диалога, определение критерия, политика, версия промпта, модель)). Повторная оценка, пересчёт отчёта, новая версия чек-листа с неизменными критериями — 0 вызовов. Все 65 DEV-диалогов закэшированы и закоммичены.
2. **Один вызов судьи на диалог** (все 8 критериев в одном запросе; батчирование по 3 — только для локальных моделей ≤ 8B, `CQA_JUDGE_BATCH`).
3. **Валидатор без модели**; повторный запрос — максимум один, и только для нарушенных критериев; дальше — автоисправление и консервативный ответ по правилам, а не третий вызов.
4. **Проверяющая модель только для неуверенных результатов**: для alem по умолчанию `CQA_VERIFY=low` — проверяются результаты с уверенностью < 0,75 (`CQA_VERIFY_THRESHOLD`), а не все.
5. **Резерв**: при остатке ≤ 20 % лимита (или `CQA_ALEM_RESERVE` запросов) судья автоматически переключается на резервную модель `fallback`; при 429 — пауза `retry-after` и переключение.
6. **Офлайн-режим** (`CQA_PROVIDER=offline`): воспроизведение из кэша; промах кэша — явная ошибка, а не тихий вызов. Калибровка имеет флаг `--cache-only`, который отказывается стартовать, если потребовался бы хотя бы один живой вызов.
7. **Правила вместо модели там, где они точнее** (`config/routing.json`: 02, 03, 07) — модель всё равно вызывается один раз на диалог, но её ответ по этим критериям используется как второе мнение, и повторная оценка после правки правила не требует вызова.

## 3. Каскад (одна оценка = диалог × версия чек-листа)

1. **Факты** (0 вызовов): первая/последняя реплика оператора, событие подтверждения личности, сигналы раскрытия/оскорбления/обхода, паузы, обрыв. Для критериев `evaluator: rule:*` это и есть ответ.
2. **Кэш** по критерию.
3. **Судья** — 1 вызов на диалог.
4. **Валидатор** (0 вызовов) → при нарушениях один `repair` → автоисправление → консервативный ответ по фактам с уверенностью ≤ 0,5.
5. **Проверяющая модель** — только для неуверенных результатов (см. выше); расхождение понижает уверенность и попадает в `review_reasons`.
6. **KZ-диалоги** — второе мнение `kazllm`, 1 вызов; расхождение понижает уверенность и попадает в `review_reasons`.
7. **Маршрутизация** (0 вызовов): для критериев 02/03/07 окончательное решение — детерминированное, модель — второе мнение.

Измерено: **2,2 вызова на диалог** в среднем (138 / 64) при выключенной проверяющей модели; с ней — до 3,2 (RU/EN) и 4,2 (KZ).

## 5. ОЦЕНКА (не понесённые расходы): тот же объём токенов на платной модели

Формула — буквально измеренные токены из `reports/runs/alem_qwen3-8.json` × цены за 1M токенов из `services/evaluator/pricing.js` (цены в этом файле записаны разработчиками; перед цитированием жюри их стоит сверить с действующим прайс-листом поставщика — в репозитории дата сверки не зафиксирована):

```
cost_run      = (T_in × P_in + T_out × P_out) / 1e6
cost_dialog   = cost_run / 64                       (64 диалога с живыми вызовами)
cost_month(N) = cost_dialog × N
T_in = 688 731, T_out = 165 494  (судья + repair + kz, проверяющая модель выключена)
```

| Модель (прайс-лист `pricing.js`, $/1M вход / выход) | cost_run | cost_dialog | N = 50 000/мес | N = 100 000/мес |
|---|---|---|---|---|
| `claude-haiku-5-5` ($0,10 / $0,50) | $0,152 | $0,0024 | ≈ $118 | ≈ $237 |
| `claude-sonnet-5-5` ($2 / $10) | $3,03 | $0,047 | ≈ $2 369 | ≈ $4 738 |
| `claude-opus-5-5` ($4 / $20) | $6,06 | $0,095 | ≈ $4 738 | ≈ $9 476 |
| alem.plus `qwen3-8` (измерено) | **$0** | **$0** | **0 ₸** — ограничение не деньги, а квота запросов и пропускная способность | |

Что эта оценка не учитывает: (а) проверяющую модель (в измеренном прогоне выключена; при `CQA_VERIFY=low` добавится < 1 вызова на диалог ≈ 4k/0,5k токенов); (б) кэширование промпта у облачных провайдеров (системный промпт ≈ 3–4k токенов повторяется в каждом вызове и у Anthropic оплачивался бы по цене чтения кэша — реальная цифра была бы **ниже**); (в) 92 % repair-запросов — это свойство `qwen3-8` + текущего валидатора; без repair тот же расчёт даёт $0,0016 / $0,032 / $0,063 на диалог (Haiku / Sonnet / Opus). Иными словами, repair удорожает оценку в полтора раза, и его доля — первая цель оптимизации промпта.

Пропускная способность на alem при `concurrency 3`: 545 с на 65 диалогов → ≈ 10 300 диалогов/сутки с одного процесса, если квота позволяет; реальный предел задаёт квота (200 запросов на окно неизвестной длины), а не время.

Единственный облачный вызов за всё время разработки: один тестовый запрос к `claude-haiku-5-5` для проверки формата ответа CLI (≈ $0,0004 по прайс-листу; результат не кэшировался).

## Summary (EN)

Zero-spend policy. Measured on the alem.plus free API (Kazakhstan), judge `qwen3-8` (thinking disabled), file `reports/runs/alem_qwen3-8.json`: 65 DEV dialogs (64 live + 1 cached), **138 calls** (64 judge, 59 repair, 15 Kazakh second opinions, 0 verifier), **688 731 input / 165 494 output tokens** (≈ 10.8k / 2.6k per dialog), **545 s wall at concurrency 3 = 8.4 s/dialog throughput, 21.8 s mean per-dialog latency** (median not persisted), **0 USD / 0 ₸**. 92 % of judge answers needed one validator-driven repair call; 1 % of criterion results fell back to rules. The shared quota header showed 200 requests with an unknown reset window, so the product protects it with a per-criterion cache (all 65 dialogs cached; every later calibration ran with 0 calls), a single judge call per dialog, at most one repair, verifier only for low-confidence results, a 20 % reserve with automatic fallback model, and a strict offline mode (`--cache-only`). The table in §5 is a list-price **ESTIMATE, not incurred**: the same measured token volume would cost about $0.0024 (Haiku) / $0.047 (Sonnet) / $0.095 (Opus) per dialog using the prices recorded in `services/evaluator/pricing.js` (re-verify against the vendor price page before quoting).
