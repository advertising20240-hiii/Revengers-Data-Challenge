## Бюджет вызовов модели (главный риск дня)

Измерено на DEV (`reports/runs/alem_qwen3-8.json`, разбор в `docs/COST.md` §1–2): 65 диалогов → 64 вызова судьи + 59 повторных запросов после валидатора + 15 вызовов казахской модели = **138 вызовов**; 545 с стены при `CQA_CONCURRENCY=3` (≈ 8.4 с/диалог пропускной способности, 21.8 с задержка одного диалога). Заголовки alem.plus показывали общий лимит **200 запросов** с неизвестным окном сброса — один прогон съедает почти всю квоту. Поэтому порядок строгий:

1. **Один пробный вызов** до набора: «Оценить выбранные» на одном DEV-диалоге с принудительной переоценкой **или** любой одиночный вызов — затем прочитать остаток квоты: `GET /api/health → provider.quota` (`x-ratelimit-*-remaining` по моделям; поле появляется после первого живого вызова). Записать число **R**.
2. **`CQA_VERIFY=off`** в `.env` на контрольный день (проверяющая модель `gpt-oss` в измеренных прогонах и так была выключена; её вклад не измерен — нечего терять).
3. **KZ-второе мнение только если R ≥ 2·N + 15**, где N — число диалогов в контрольном наборе (судья + возможный повтор на диалог = 2 вызова, плюс резерв). Иначе убрать `ALEM_MODEL_KZ` из `.env` (роль `kz` → «не задана») и перезапустить сервер.
4. **Сначала демо-шортлист**: выбрать в таблице 5–6 контрольных диалогов, которые пойдут в карточки на выступлении (RU, KZ, EN, со звонком, если есть), → «Оценить выбранные». Потом «Оценить все» на остальных. Так даже при обрыве квоты карточки для демо готовы.
5. **Резерв ≥ 15 вызовов** на живую замену критерия (новый критерий × 3–5 диалогов симуляции + применение). Если после основного прогона R < 15 — замену критерия показывать правилом «Скорость первой реакции» (0 вызовов).
6. **Один вызов судьи на диалог** — не запускать «Оценить все» дважды; не нажимать «Второе мнение ИИ» до выступления. Кэш по критерию (`data/cache/eval/`) делает повторный прогон бесплатным, но только для неизменённых критериев.
7. **Порядок при отказе**: 429/квота → автоматически резервная модель (`ALEM_MODEL_FALLBACK`, срабатывает при остатке ≤ 20 % лимита) → если и она недоступна: `CQA_PROVIDER=heuristic` — детерминированные правила по всем критериям, 0 вызовов, в интерфейсе источник решения помечен «детерминированное правило»; качество ниже (на DEV точность 04 81.5 %, 06 66.2 %, итог точно 49.2 %), но итог будет у каждого диалога → `CQA_PROVIDER=offline` только для показа DEV. **Ollama на ноутбуке не установлена** — как резерв не рассматривать.

## Если

| Ситуация | Действие |
|---|---|
| API организаторов не отвечает | файл от организаторов → «Загрузить файл»; формат тот же |
| alem.plus 429 / квота | автоматически резервная модель; затем `CQA_PROVIDER=heuristic` (все диалоги оценены правилами, без модели, источник помечен в карточке); на демо честно сказать «контрольный набор оценён правилами из-за лимита бесплатного API, DEV — моделью» |
| Провайдер недоступен и правила не подходят | `CQA_PROVIDER=offline`: показываем DEV; замену критерия показываем правилом `first_reaction` |
| Сервер не стартует | второй ноутбук; `node server/index.js` напрямую, проверить `PORT` |
| Push не проходит | коммит и тег локально, повторить с токеном; ссылка уже отправлена — жюри проверяет зафиксированный коммит |
