# Ограничения (честный список)

Что прототип не делает или делает с оговорками. Каждая цифра — из файла в `reports/`; методика — `docs/EVALUATION.md`, стоимость — `docs/COST.md`. Снимок на 2026-11-08 (ночь) после живого прогона `reports/runs/alem_qwen3-8_v6_rules.json` и пересчёта `reports/calibration.json`, эталон v1.1; первичны файлы отчёта.

## Оценка и её измерение

- **Цели точности §9.1 на всех 65 достигнуты, κ — не у всех.** Эталон v1.1: бинарные 01, 02, 03, 05, 07, 08 — 93,8–100 % (цель ≥ 92 %); шкалы: 04 — 96,9 % точно / 100 % ±1 шаг, 06 — 86,2 % / 93,8 % (цель ≥ 70 / ≥ 90); грубые ошибки 8/8 без ложных. κ ≥ 0,61 на holdout не выполнено у **06 (0,40, ДИ [0; 0,77])** и формально у 05 (0,608, ДИ [−0,07; 1]).
- **06 «Ведение диалога» — самый слабый критерий: 86,2 % на всех 65, 85 % на holdout.** В v6 ожидание стали считать от последнего сообщения клиента, а сбоем — только необъявленное ожидание дольше 3 минут (порог первой реакции, ответ организаторов); ступени описаны явно. После этой правки модель иногда **мягче разметчика**: 11 из 13 строгих расхождений — оценка выше эталона, 6 из них — сразу на две ступени (эталон 4, модель 10: клиенту пришлось переспросить, а модель этого не учла; например, `p1-kz-005`, `p1-ru-016`, `p1-en-015`). Поэтому ±1 шаг по 06 — 93,8 %, а не 100 %, как в v5, и на holdout 06 упал с 95 до 85 %.
- **02 «Выявление потребности» — по-прежнему спорная граница.** 93,8 % на всех 65 (holdout 90 %) после правки v6: N/A — по умолчанию, когда детали уже известны (в т.ч. из ответов боту), «Да» — только за собственный уточняющий вопрос оператора, в коде — защита «нет вопроса оператора → N/A». Защита проверяет лишь наличие вопросительного знака в репликах оператора, а не то, был ли вопрос уточняющим; оставшиеся 4 расхождения — граница «Нет» / N/A / «Да» (в том числе в звонках).
- **07 «Завершение» оценивается по буквальной формулировке чек-листа**: «Да» — только прощание **и** итог / следующий шаг / предложение дальнейшей помощи; вежливое «Пожалуйста. Хорошего дня!» после благодарности клиента — «Нет». Так мы прочитали чек-лист после ответа организаторов на прямой вопрос («Внимательно перечитайте чеклист по данному пункту»); эталон пересмотрен под это прочтение (v1.1, 31 диалог, причина в `tests/gold/dev_labels.json → revisions`, прежняя версия — `dev_labels.v1.0.json`). Правило и эталон следуют одной формулировке, поэтому 95,4 % по 07 — согласие с этим прочтением; если организаторы на контроле прочитают иначе, оценки 07 у вежливых прощаний разойдутся с их ожиданием. Список вежливых формул (`COURTESY_RE` в `services/evaluator/rules.js`) — RU/KZ/EN, проверен на DEV; новая формулировка прощания может потребовать дополнения списка.
- **06 исправлялось трижды при открытых результатах по всем 65.** v3 — уточнение подсказки к ступеням; v5 — оценка 06 отдельным вызовом (в общем вызове на все критерии 70,8 %, отдельно — 84,6 %); v6 — ожидание от последнего сообщения клиента, порог 3 минуты, явные ступени. Решения общие (ID диалогов никуда не вшиты, v6 опирается на ответы организаторов), но приняты с учётом holdout, поэтому holdout по 06 (и по 02/04 после v6) уже не полностью «непросмотренный».
- **Разброс модели между прогонами реален**: по 02 прогон v3 дал 95,4 %, v4 — 89,2 % при той же модели и том же шаблоне промпта (изменилась только строка 07 политики, из-за чего переоценены все критерии); в v6 06 на всех 65 вырос, а на holdout упал.
- **Первый отчёт содержал ошибочный вывод.** Цифры v1 «модель 16,9 % на 03, 46,2 % на 02» были в основном дефектом нашего валидатора (N/A модели читался как нарушение → 92 % диалогов в repair, 5 откатов к правилам). После исправления модель даёт на 03 95–98 %; маршрутизация перевыбрана, правила решают только 03 и 07. Файл `reports/runs/alem_qwen3-8.json` сохранён как история, а не как характеристика модели.
- **Выигрыш гибрида над моделью мал, а на holdout его нет**: на всех 65 — два диалога по 07 и MAE итога 5,28 против 5,54; на holdout правило 07 ошибается в одном диалоге, где модель права (95 против 100 %), и гибрид чуть хуже чистой модели (MAE 6,37 против 6,12). Ценность маршрутизации — детерминизм и независимость от квоты на 03/07, а не прирост точности.
- **Итоговый балл совпадает с эталоном точно в 63,1 % диалогов** (в пределах ±5 — 67,7 %, MAE 5,28; holdout — 60 % и 6,37): одна несовпавшая метка в 100-балльной формуле сдвигает итог на 5–20 баллов.
- **Эталон маленький, одиночный и командный.** `tests/gold/dev_labels.json` размечен участниками команды по чек-листу Freedom, а не организаторами: 65 диалогов (60 синтетических чатов + 5 реальных звонков; RU 35 / KZ 15 / EN 15), один разметчик, второго нет — межразметчиковая согласованность неизвестна. Holdout — 20 диалогов: 95 % ДИ шириной 15–30 п.п.; один диалог = 5 п.п. Любую цифру цитировать с интервалом (`criteria[].holdout.accuracy_ci`).
- **Маршрутизация выбиралась на этих же данных** (tune 45). Holdout — честная оценка, но распределение DEV ≠ реальные диалоги Freedom; при другом формате системных событий правило 03 нужно перемерять.
- **κ по шкалам 04/06 умеренная (0,70 / 0,51 на всех 65; holdout 0,71 / 0,40)** в том числе из-за парадокса распространённости: 72 % / 68 % эталонов на верхней ступени, p_e 0,59 / 0,59. Показываем p_e и матрицы ошибок рядом, κ не прячем.
- **Test–retest измерен на 20 диалогах** (96,9 % идентичных меток, `reports/runs/retest_injection.json`) — **на более ранней версии политики**, до правок 07 (v4), отдельного вызова для 06 (v5) и правок 02/04/06 (v6); после этого не повторялся. На всех 65 и на контрольном наборе не повторялся (квота).
- **Проверка на инъекцию** — один синтетический случай с живой моделью (устойчив, та же ранняя версия политики) и юнит-тест обрамления; систематического набора атак нет.
- **Проверяющая модель (`gpt-oss`) в измеренных прогонах `qwen3-8` выключена** (`--no-verify`): её вклад как проверяющей не измерен. В продукте включается только для результатов с уверенностью < 0,75. В роли судьи `gpt-oss` измерен на holdout и оказался заметно хуже `qwen3-8` (02 — 35 %, 04 — 70 %, MAE итога 15,73; `reports/runs/alem_gpt-oss_holdout.json`), поэтому судьёй он не используется.
- **Самооценка уверенности модели не калибрована.** Калиброваны (по tune) только уверенности 03/07 (`config/routing.json`). Порог 0,6 для очереди проверки выбран вручную.
- **Цикл обучения** — few-shot из решений проверяющего, не дообучение. Эффект не измерен (`learning_loop: null`); улучшения не заявляем. Ключ кэша не включает примеры — они действуют на новые диалоги или при принудительной переоценке.
- **Казахский.** Гибрид даёт KZ 95,8 % по всем меткам (15 диалогов, ДИ [90,6; 98,2]) и 100 % на holdout при 5 диалогах — выборка слишком мала для вывода «казахский не хуже». Казахское второе мнение (`kazllm`) в v6 расходилось с судьёй 3 раза при 14 вызовах (в v4 и v5 — по 2 раза на 15 KZ-диалогов); кто прав при расхождении — не измерено.
- **Критерий 03** опирается на системное событие подтверждения личности и, для звонков, на устную идентификацию (ФИО/ИИН/адрес/SMS-код) в репликах — лексиконный сигнал, проверенный на 5 звонках DEV; другой контакт-центр потребует настройки лексикона.
- **Голос.** Транскрипты звонков — распознавание речи с ошибками; дикция, интонация, перебивания не оцениваются — аудио модели не передаётся.
- **Критерий 05 «Эмпатия»** оценивается по текстовым действиям; эмоции не выводятся.
- **Стоимость и квота.** 0 ₸ для команды — API Alem Plus (llm.alem.ai) по ключам, предоставленным организаторами хакатона; публичные тарифы платформы не опубликованы, стоимость в продакшене требует уточнения. Заголовки ответа показывали лимит 200 запросов с неизвестным окном сброса; полная оценка 65 диалогов текущим продуктом (два вызова судьи на диалог + казахское мнение) — 143 запроса в прогоне v6. Продукт защищается кэшем, резервом 20 %, деградацией к правилам с честной подписью и офлайн-режимом, но живая демонстрация на незакэшированном диалоге может упереться в квоту.
- **Локальная модель (Ollama) не запускалась** — не установлена на машине разработки; качество на локальной модели не измерено.
- **Медиана задержки не сохраняется** в отчёте калибровки — только среднее (в v6 — 33,5 с на диалог для обоих вызовов судьи и казахского мнения; в v4 + v5 было 12,8 + 3,5 с); по-вызовные задержки есть в трассе каждой живой оценки.

## Продукт

- **Без аутентификации.** Роли «Оператор / Проверяющий» — переключатель интерфейса (разрешено условиями задания). Для продуктивного контура нужны роли безопасности (`docs/DYNAMICS365.md`).
- **Хранилище — JSON-файлы.** Достаточно для десятков тысяч оценок на одной машине; для нескольких серверов нужна БД или Dataverse.
- **Dynamics 365.** Собран один HTML-файл веб-ресурса и описано соответствие таблиц; решение Dataverse не развёрнуто, PCF-контрол не создан.
- **Экспорт** — CSV, печать карточки из браузера (кнопка «Печать», отдельные стили для печати) и файл результатов организаторов `results/dev/results.json` (JSON 1.0, `npm run export:results`, по активной версии чек-листа или `--checklist <версия>`); XLSX и PDF-отчёт не реализованы.
- **Интерфейс** — RU · ҚАЗ · EN с переключателем в шапке (`public/i18n/`). Названия критериев, секций и объяснения модели остаются на языке чек-листа (русском); цитаты-доказательства — на языке диалога.
- **Сервер по умолчанию слушает только `127.0.0.1`.** Чтобы открыть его в сети (контейнер за прокси), нужен явный `HOST=0.0.0.0` — и тогда аутентификация обязательна (`docs/SECURITY.md`).
- **Статическое демо** (`npm run build:static`, GitHub Pages) — только просмотр снимка DEV: оценка, апелляции, сохранение чек-листа и прослушивание записи через прокси в нём не работают (`docs/DEPLOY.md`).
- **Аудио** проксируется с `Range` только для `audio_url` загруженного диалога и только на публичные http(s)-адреса; если источник не отдаёт запись, предлагается открыть `audio_url` напрямую.
- **Загрузка набора по `group_id`** — только с адреса API организаторов из настроек сервера (`CQA_DATA_URL`); другой источник — через «Загрузить файл».
- **Шаблоны критериев** — 6; произвольные детерминированные правила (`rule:<name>`) требуют реализации в `services/evaluator/rules.js` — единственный случай, когда новый критерий требует кода.

## Данные

- DEV-набор синтетический (60 чатов) + 5 реальных звонков; поведение на реальных чатах Freedom не проверено.
- «Плохих» диалогов мало: по 04 всего 9 эталонов ≤ 10 баллов из 65, по 06 — 21 ниже верхней ступени; редкие классы измерены на единицах примеров.

## Что в дорожной карте

Граничные примеры для ступеней 4 / 7 / 10 критерия 06 (модель пропускает переспрашивание клиента); граница «Нет» / N/A для 02 в звонках; повтор test–retest и инъекции с живой моделью на текущей версии политики; второй разметчик и межразметчиковая κ; подтверждение прочтения критерия 07 у организаторов на контрольном наборе; калибровка самооценки уверенности модели; измерение эффекта цикла обучения; распознавание речи для звонков (дикция); Dataverse и PCF-контрол; SLA апелляций; XLSX/PDF; перевод названий критериев чек-листа на KZ/EN.
